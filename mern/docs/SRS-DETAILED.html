1. Introduction

1.1 Purpose

This SRS defines what the TechNexa system must do, who uses it, how the modules interact, what data is stored, and which quality attributes the implementation satisfies. It is written for the project supervisor, examination committee, developers, testers and future maintainers. Every requirement is paired with its implementation detail and, where applicable, a screenshot of the interface that realises it.

1.2 Scope

TechNexa is a browser-based platform that combines:

  • A public IT-services and training website with service, course, industry and legal pages.
  • A course catalogue and secured enrollment flow (login required).
  • A role-based learning portal for students, teachers and administrators.
  • Academic features: assignments, quizzes, attendance, marks, timetable, materials, fees and documents.
  • Real-time private chat, presence, audio/video calls and mixed-audio call recording.
  • Administrative reporting, audit logs, payment tracking and communication tools.
  • Light and dark themes across the public site and portal.

Out of scope: payment gateway integration, native mobile app, full conferencing recorder, external LMS migration, and third-party SSO. These are listed as future work.

2. Overall Description

2.1 Product Perspective

TechNexa is a feature-based monorepo. The React SPA communicates with an Express REST API. MySQL stores relational data. Socket.IO handles real-time chat, presence and call signalling; WebRTC handles peer-to-peer audio/video. The platform replaces disconnected static pages and manual academic records with one authenticated system whose navigation and API permissions depend on the user's role.

2.2 Design Constraints

  1. The accurate stack name is React + Node.js + Express + MySQL (not MERN) because the database is relational.
  2. Authentication uses a JWT in an httpOnly cookie; tokens are never exposed to JavaScript.
  3. All protected API routes verify authentication and role on the server.
  4. Uploaded files are stored outside the web root and served only through authenticated routes.
  5. All timestamps are stored and compared in UTC.
  6. The UI is responsive across desktop, tablet and mobile.
  7. Core academic features do not depend on a paid external service; AI quiz generation is optional with a built-in fallback.

4.3 Theme, Accessibility & Responsiveness FR-UI

  • Light/dark theme (UI-01..04): ThemeContext.jsx stores technexa_theme in localStorage; theme-init.js applies saved/OS theme before paint; ThemeToggle.jsx on public, auth and portal layouts; theme CSS in global.css, site.css, portal.css.
  • Consistent course cards (UI-06): equal-height cards with bottom-aligned buttons in site.css.
  • Responsive (UI-07): media queries across stylesheets; mobile nav drawer in PublicLayout.jsx.
  • Icons (UI-08): Font Awesome only; no chevrons/arrows/rocket icons.
  • Call button on touch only: .call-btn-mobile hidden on non-touch devices via (pointer: coarse) check in script.js (legacy) — see Screenshot 1 of the security report.

4.4 Security Implementation NFR-SEC

  • SEC-01/02: bcrypt (cost 12) hashing; JWT in httpOnly, SameSite=Lax cookie; 5-minute expiry.
  • SEC-03/04: parameterised SQL everywhere; requireAuth/requireRole on every protected route.
  • SEC-05/06: extension allow-list + size caps + magic-byte check (verifyMagic); private upload dirs; recordings limited to participants/admin.
  • SEC-07/08: SHA-256-hashed, one-hour reset tokens; login throttle 6 fails/15min; fail2ban on host.
  • SEC-09/10: secrets in environment/k8s secret; CSP, Referrer-Policy, Permissions-Policy, COOP, Origin guard; HTTPS-ready (Secure cookie when NODE_ENV=production).
  • Enrollment auth gate (added): POST /api/enroll returns 401 for guests; UI shows register/login gate — documented with screenshots in SECURITY-HARDENING-FULL.pdf.

4.5 Deployment & Operations FR-OPS

  • OPS-01: START-TECHNEXA.bat, start-all.ps1, start-dev.bat one-command launchers.
  • OPS-02/03: numbered migrations in server/database/; db:seed creates demo accounts and sample data.
  • OPS-04: GET /api/health health check.
  • OPS-05: Dockerfile.server, Dockerfile.client, deploy/nginx/default.conf, .github/workflows/ci.yml.
  • OPS-06: .gitignore excludes .env, uploads, secrets; only .env.example tracked.

6. Architecture & Data

Layers: React SPA (presentation) → Express REST API (routing, validation, auth) → business logic (enrollment, grading, quiz scoring, AI fallback, call metadata) → mysql2 pool (parameterised SQL) → MySQL tables + private upload directories. Socket.IO adds real-time chat/presence/call signalling; WebRTC carries media; SMTP sends reset email; OpenAI/Gemini is optional for question generation.

Main entities: User, Student profile, Teacher profile, Course, Enrollment, Payment, Assignment, Submission, Quiz, Quiz question, Question bank, Quiz attempt, Quiz violation, Attendance session/record, Timetable, Material, Document, Notice, Announcement, Chat message, Chat attachment, Call log, Login log, Password reset, Contact message, Subscriber. All timestamps are UTC. Full schema is in DATABASE.md.
